```text

  result if it matches ^E\d{4}$, else None.
- tenure_months(hire_date: date, as_of: date) -> int: whole calendar months completed,
  i.e. (years*12 + months), minus 1 if as_of's day-of-month is before hire_date's.

                    as_of: date = config.REFERENCE_DATE) -> dict[str, Any]

  Errors are RETURNED as dicts, never raised (REQUIREMENTS §7: the model must be able to
  reason about them):
    - input fails normalisation (including empty string): {"error": "INVALID_EMPLOYEE_ID", "employee_id": <raw input as given>}
    - valid format but not in the directory: {"error": "EMPLOYEE_NOT_FOUND", "employee_id": <normalised id>}
- The function must not read the system clock and must not do I/O. The directory is passed in.

- " e1001 " and "e1001" both normalise and return E1001's record
- tenure_months: same day = whole month counted; day before = not counted
  (2021-06-14 to 2026-11-14 is 65; to 2026-11-13 is 64); same date is 0
- as_of is respected: E1001 with as_of=date(2022, 6, 14) gives tenure_months 12

Comment WHY at each non-obvious decision (errors as data, sorted equipment, no clock).
```

### Prompt 3 of 4: Structured JSON logging

```text
You are working in a Python 3.14 repo (src/ layout, package `it_requests`). Read
markdowns/PLAN.md section 5 ("Logging") first.

GOAL: a small structured-logging module used by both the MCP server and (later) the agent.
Standard library `logging` only, no new dependencies.

Follow CLAUDE.md: tests first (in tests/unit/test_observability.py), show them failing, then stop for "go".

FILE: src/it_requests/observability.py
- request_id_var: contextvars.ContextVar[str | None], default None. Explain in a comment that
  a ContextVar keeps the ID correct per request even with async code, unlike a global.
- REDACTED_KEYS: frozenset of field names never written to logs: {"name", "api_key",
  "authorization", "password", "token"}. Values for these keys are replaced with "[REDACTED]".
- class JsonFormatter(logging.Formatter): each record becomes ONE line of JSON with keys:
  "ts" (UTC ISO-8601 with milliseconds and "Z"), "level", "component" (the logger name),
  "event" (record.getMessage()), "request_id" (from request_id_var), plus every key/value in
  the dict passed as extra={"fields": {...}}, after redaction. Use json.dumps(default=str)
  so dates serialise. Exceptions: if record.exc_info is set, add "exc_type" and "exc_message".
- log_event(logger: logging.Logger, event: str, level: int = logging.INFO, **fields: Any) -> None:
  the one helper everything calls, so call sites stay short and consistent.
- configure_logging(component: str, *, log_file: Path | None = None, level: int = logging.INFO)
  -> logging.Logger: returns logging.getLogger(component) with a stderr StreamHandler using
  JsonFormatter, plus a FileHandler if log_file is given (create parent dirs). It must be
  idempotent: calling it twice must not add duplicate handlers. Set propagate = False.

TESTS (tests/unit/test_observability.py). Capture output with a StringIO handler that uses
JsonFormatter (or caplog plus the formatter):
- a log_event call produces a single line that json.loads parses, with ts, level, component,
  event and the custom fields
- ts ends with "Z" and parses with datetime.fromisoformat
- request_id is null by default, and equals the value set with request_id_var.set(...);
  reset the var afterwards using the token
- the field "name" (and "api_key") is written as "[REDACTED]", and the real value appears
  nowhere in the line
- a date value serialises as an ISO string
- configure_logging called twice leaves exactly the same number of handlers
- configure_logging with log_file=tmp_path / "logs" / "app.jsonl" creates the file and writes JSON lines to it
- an exception logged via logger.exception adds exc_type and exc_message

Comment WHY at each non-obvious decision.
```

**Why now and not later:** PLAN §5 makes structured logs part of every milestone's definition of done. The server in Prompt 4 should log from its first line, not have logging retrofitted later. Redaction is tested now, so employee names can never leak into logs by accident.

## Part 4: PR description (paste into GitHub)

**Title:** `M1: get_employee_info end to end, plus JSON logging`

```markdown
## What

Milestone M1 (brief steps 2 and 3): the first real tool, built as a plain tested function,
then exposed over MCP and called from a client.

- `data/employees.json`: the six mock employees from REQUIREMENTS §8, with `data_version`
  and `effective_date` lineage fields.
- `data.py`: Pydantic models and `load_employees()`. Bad data (duplicate IDs or asset IDs,
  unknown roles, statuses or items, bad or out-of-order dates, unknown fields) fails loudly
  with `DataValidationError`.
- `employees.py`: `get_employee_info()` as a pure function, implementing REQUIREMENTS §7.1.
  Input is normalised (`" e1001 "` becomes `E1001`), errors are returned as data
  (`INVALID_EMPLOYEE_ID`, `EMPLOYEE_NOT_FOUND`), tenure is in whole months, and `as_of` is
  injected (no system clock).
- `observability.py`: one-line JSON logs with `request_id` from a ContextVar. Sensitive
  fields (`name`, `api_key` and others) are redacted.
- `server.py`: the real MCP server. `build_server()` registers `get_employee_info` as a thin
  wrapper that logs a `tool.call` event for every call. `main()` serves streamable HTTP on
  127.0.0.1:8000.
- `scripts/client_demo.py`: calls the tool over HTTP (screenshot for deliverable #2).
- CI: the integration-test workaround is removed, and the 90% coverage threshold is now
  checked across unit and integration tests together.

## Why

The brief asks for the first tool to be a plain function with unit tests before any MCP
wrapping, and for one tool to be proven end to end before the rest are added. Validation at
load and errors-as-data follow PLAN §3 and REQUIREMENTS §7. Logging starts now, so every
later tool logs the same way.

## How it was built

Test-first throughout: each step has a separate red commit (failing tests) followed by a
green commit (implementation).

## Testing

- `make check`: format, lint, mypy --strict, unit and integration tests, coverage ≥ 90%,
  pip-audit.
- Unit tests cover the normal case, unknown ID, bad formats, normalisation, tenure boundaries
  and every data-validation failure.
- The integration test calls the tool through the MCP protocol in-process.
- Manual run: `make serve` plus `make client-demo` (screenshot #2).

## Not in this PR

`get_policy_limits`, `check_request_eligibility` and `flag_for_human_review` (M2 to M4).
Tracing and cost tracking (M5).
```
