### Prompt 2 of 3: `get_policy_limits` as a plain function

```text
Read markdowns/REQUIREMENTS.md section 7.2 and the get_policy_limits row of section 12.1,
src/it_requests/data.py (PolicyTable) and src/it_requests/employees.py (the style to match:
pure function, errors as data, data_version in every success response).

GOAL: implement get_policy_limits as a PLAIN, PURE function to the §7.2 contract.

Follow CLAUDE.md: tests first (in tests/unit/test_policy.py), show them failing, then stop for "go".

FILE: src/it_requests/policy.py
- normalize_role(raw: str) -> Role | None: strip and lower-case; return it if it is one of
  ROLES, else None. (Case-insensitive per §7.2.)
- get_policy_limits(role: str, *, policy: PolicyTable) -> dict[str, Any]
  Success:
    {"role": <normalised role>,
     "limits": {<item>: {"max": int, "refresh_months": int | "none" | None}, ...},
     "data_version": policy.data_version}
    - "limits" has all six items, in CATALOG_ITEMS order (deterministic output)
    - refresh_months is passed through exactly: an int, the string "none", or None (JSON null)
  Error (returned, never raised):
    {"error": "UNKNOWN_ROLE", "role": <raw input as given>}
  No I/O, no clock.

TESTS (tests/unit/test_policy.py). Load the real policy once with a module-scoped fixture:
- "standard" returns all six items, in CATALOG_ITEMS order, with laptop {"max": 1,
  "refresh_months": 36}, docking_station {"max": 1, "refresh_months": "none"} and
  mobile_phone {"max": 0, "refresh_months": None}; data_version "policy-v1"
- parametrize over all four roles: six items each, and max values match REQUIREMENTS §4.1
- contractor: laptop, monitor and docking_station all max 0 with refresh None
- "Manager", " ENGINEER ", "Contractor" normalise to lower case
- "intern", "", "admin" return {"error": "UNKNOWN_ROLE", "role": <raw>} with the raw input echoed
- the result is JSON-serialisable (json.dumps works) and refresh None becomes null
- parametrize normalize_role over valid and invalid inputs

Comment WHY at each non-obvious decision.
```

**Why `refresh_months` passes through unchanged:** the tool's output is what the agent explains to the employee. If the tool turned `"none"` into a number or dropped `null`, the agent could state an entitlement the policy never gave, which would break constraint C4.

## Part 4: PR description (paste into GitHub)

**Title:** `M2: get_policy_limits`

```markdown
## What

Milestone M2 (brief step 4, second tool): role entitlements as validated data and a pure
function, exposed as the second MCP tool.

- `data/policy.json`: the REQUIREMENTS §4.1 matrix (4 roles x 6 items) with
  `data_version` and `effective_date`.
- `data.py`: `ItemLimit` and `PolicyTable` models and `load_policy()`. The REQUIREMENTS v1.1
  rule is enforced at load: `max: 0` must have `refresh_months: null` (not entitled), and
  `max > 0` must have a positive interval or `"none"` (no refresh cycle). Missing roles or
  items fail loudly. The employee and policy loaders now share one error-handling helper.
- `policy.py`: `get_policy_limits()` as a pure function (REQUIREMENTS §7.2). Role lookup is
  case-insensitive, all six items come back in catalog order, `UNKNOWN_ROLE` is returned as
  data, and `data_version` is in every success response.
- `server.py`: `get_policy_limits` registered with the §7.2 description, and
  `build_server()` now takes the policy too. Both tools log through one shared helper.
  `get_employee_info` log lines now include `resolved_employee_id`.
- `scripts/client_demo.py`: also calls `get_policy_limits`.

## Why

The brief adds the remaining tools one at a time, in the same pattern: test the plain
function, wrap it, call it from the client. Keeping `"none"` and `null` distinct (and
enforced) means the agent never has to infer an entitlement, which supports constraint C4.
`resolved_employee_id` closes the gap noted in M1, where a successful lookup's log line
didn't say which employee it found.

## How it was built

Test-first: a red commit (failing tests) before each green commit.

## Testing

- `make check`: format, lint, mypy --strict, unit and integration tests, coverage ≥ 90%,
  pip-audit.
- Unit tests cover every role, mixed case, unknown roles, the `"none"` and `null` cases,
  and every policy-data validation failure.
- Integration tests call `get_policy_limits` through MCP in-process and check the
  description, the structured output, errors as data and the log line.

## Not in this PR

`check_request_eligibility` (M3) and `flag_for_human_review` (M4).
```
