## Part 2: Prompts for your coding agent

### Prompt 1 of 2: The eligibility function

```text
Read markdowns/REQUIREMENTS.md sections 4.1 to 4.3 (rules, date rule, quantity rule,
algorithm), 7.3 (contract), 8 (the pre-computed table) and the check_request_eligibility row
of 12.1. Also read src/it_requests/data.py, employees.py and policy.py; reuse
normalize_employee_id and the models, and match their style (pure, errors as data).

GOAL: implement check_request_eligibility as a PLAIN, PURE function that follows the §4.3
algorithm step by step, in order, stopping at the first step that applies.

Follow CLAUDE.md: tests first (in tests/unit/test_eligibility.py), show them failing, then stop for "go".

FILE: src/it_requests/eligibility.py

1. add_months(d: date, months: int) -> date
   Calendar months, with the month-end clamp from §4.2: if the target day doesn't exist,
   use the last day of that month. Use calendar.monthrange. No external libraries.

2. check_request_eligibility(employee_id: str, item: str, *, directory: EmployeeDirectory,
                             policy: PolicyTable, as_of: date = config.REFERENCE_DATE)
                             -> dict[str, Any]
   Input handling:
   - employee_id goes through normalize_employee_id (from employees.py).
   - item is stripped and lower-cased, then must be one of CATALOG_ITEMS.
   Steps, in this exact order (§4.3), each returning immediately:
   0. Bad ID format: {"error": "INVALID_EMPLOYEE_ID", "employee_id": <raw>}
   1. Employee not found: {"error": "EMPLOYEE_NOT_FOUND", "employee_id": <normalised>}
   2. Item not in catalog: {"error": "UNKNOWN_ITEM", "item": <raw item>}
   3. status != "active": NEEDS_REVIEW, rule R-STATUS
   4. role max for the item == 0: NOT_ELIGIBLE, rule R-ROLE
   5. units_held < max: ELIGIBLE, rule R-NEW
   6. refresh_months == "none": NOT_ELIGIBLE, rule R-LIMIT
   7. refresh date of the OLDEST unit <= as_of: ELIGIBLE, rule R-REFRESH-OK
   8. otherwise: NOT_ELIGIBLE, rule R-REFRESH, with next_eligible_date

   "Oldest unit" = the held unit of that item with the earliest issued_date. Break ties by
   asset_id, so the result is deterministic (E1003 holds two monitors issued the same day).
   Refresh date = add_months(oldest.issued_date, refresh_months). Eligible ON that date.

   Every non-error result has the same keys (keys that don't apply are null), so the
   agent and tests always see the same shape:
     "employee_id", "item", "status" (ELIGIBLE | NOT_ELIGIBLE | NEEDS_REVIEW), "rule_id",
     "role", "employment_status", "units_held", "max", "refresh_months",
     "oldest_issued_date", "refresh_date", "next_eligible_date",
     "replaces_asset_id", "as_of", "data_versions"
   - units_held, max, refresh_months: always filled in, except for R-STATUS, where only
     units_held is filled in (the check stops before the policy is consulted)
   - oldest_issued_date: the ISO date of the oldest held unit, or null if none is held
   - refresh_date: filled in only for steps 7 and 8
   - next_eligible_date: equals refresh_date, and is filled in ONLY for R-REFRESH
   - replaces_asset_id: the oldest unit's asset_id, ONLY for R-REFRESH-OK (REQUIREMENTS
     §10: a replacement must name the unit being returned; this never raises the employee
     above max)
   - as_of: ISO string
   - data_versions: {"employees": directory.data_version, "policy": policy.data_version}
     (the verdict depends on both files, so lineage names both)
   All dates are returned as ISO strings. No I/O, no clock.

TESTS (tests/unit/test_eligibility.py). Load the real employees and policy once
(module-scoped fixtures):

A. Every row of REQUIREMENTS §8, as ONE parametrized test with an id per row, asserting
   status and rule_id (and the error code for the two error rows):
   E1001 laptop NOT_ELIGIBLE R-REFRESH | E1001 keyboard_mouse ELIGIBLE R-REFRESH-OK |
   E1001 mobile_phone NOT_ELIGIBLE R-ROLE | E1002 monitor ELIGIBLE R-NEW |
   E1002 docking_station NOT_ELIGIBLE R-LIMIT | E1002 laptop ELIGIBLE R-REFRESH-OK |
   E1003 mobile_phone NOT_ELIGIBLE R-REFRESH | E1003 monitor ELIGIBLE R-REFRESH-OK |
   E1004 laptop NOT_ELIGIBLE R-ROLE | E1005 laptop ELIGIBLE R-REFRESH-OK |
   E1006 monitor NEEDS_REVIEW R-STATUS | E9999 laptop error EMPLOYEE_NOT_FOUND |
   E1001 standing_desk error UNKNOWN_ITEM

B. Exact values for the demo cases:
   - E1001 laptop: units_held 1, max 1, oldest_issued_date "2025-03-10",
     next_eligible_date "2028-03-10", replaces_asset_id null, as_of "2026-11-22"
   - E1002 monitor: units_held 1, max 2, next_eligible_date null, replaces_asset_id null
   - E1003 monitor: units_held 2, max 2, replaces_asset_id "MN-1031" (tie broken by
     asset_id), refresh_date "2026-04-11"
   - E1005 laptop: replaces_asset_id "LT-1650"
   - E1003 mobile_phone: next_eligible_date "2027-01-20"

C. Boundaries, using as_of injection on the real data (E1001 keyboard_mouse was issued
   2021-06-14 with a 24-month refresh, so its refresh date is 2023-06-14):
   - as_of 2023-06-14 (exactly the refresh date): ELIGIBLE, R-REFRESH-OK
   - as_of 2023-06-13 (one day before): NOT_ELIGIBLE, R-REFRESH, next_eligible_date "2023-06-14"

D. add_months:
   - 2024-01-31 + 1 = 2024-02-29 (leap year clamp, the REQUIREMENTS §4.2 example)
   - 2023-01-31 + 1 = 2023-02-28
   - 2024-02-29 + 12 = 2025-02-28
   - 2025-03-10 + 36 = 2028-03-10
   - 2021-06-14 + 24 = 2023-06-14
   - 2024-11-30 + 3 = 2025-02-28 (crosses a year end)
   - + 0 returns the same date

E. Order of the algorithm (the first matching step wins):
   - E1006 (on leave) asking for mobile_phone, which an engineer isn't entitled to:
     NEEDS_REVIEW R-STATUS, not R-ROLE (status is checked first)
   - E9999 with item "standing_desk": EMPLOYEE_NOT_FOUND, not UNKNOWN_ITEM
   - "abc" with item "laptop": INVALID_EMPLOYEE_ID

F. Input normalisation: (" e1002 ", " Monitor ") gives the same result as ("E1002", "monitor").
   The UNKNOWN_ITEM error echoes the raw item.

G. Robustness: for every employee in the data x every catalog item (36 pairs), the function
   returns without raising; status is one of the three values; rule_id is one of the six
   rule IDs; and ELIGIBLE never comes with next_eligible_date set.

H. Shape: every non-error result has exactly the keys listed above.

Comment WHY at each non-obvious decision (step order, tie-break, why replaces_asset_id,
why one fixed key set).
```

**Why the robustness test (G):** the table in §8 covers 13 hand-picked cases. Running all 36 employee-item pairs checks that the function never crashes or returns a nonsense verdict for a combination nobody thought to list. That matters because the agent can ask about any pair.

**Why `replaces_asset_id`:** REQUIREMENTS §10 says an approval under R-REFRESH-OK must name the old unit to return. If the tool doesn't return it, the agent would have to guess which asset to name, which breaks C4 (no facts that didn't come from a tool).

## Part 4: PR description (paste into GitHub)

**Title:** `M3: check_request_eligibility`

```markdown
## What

Milestone M3 (brief step 4, third tool): the deterministic eligibility verdict. This is the
only source of truth for approve or deny (constraints C1 and C2).

- `eligibility.py`:
  - `add_months()` handles calendar months with the month-end clamp
    (2024-01-31 + 1 month = 2024-02-29).
  - `check_request_eligibility()` is a pure function that follows the REQUIREMENTS §4.3
    algorithm step by step: invalid ID, then employee not found, then unknown item, then
    R-STATUS, R-ROLE, R-NEW, R-LIMIT, R-REFRESH-OK, R-REFRESH.
  - Every verdict has the same set of keys. It includes `next_eligible_date` (R-REFRESH
    only), `replaces_asset_id` (R-REFRESH-OK only, so a replacement always names the unit
    to return) and `data_versions` for both data files.
  - Ties between units issued the same day are broken by `asset_id`.
- `server.py`: `check_request_eligibility` registered with the §7.3 description, and its
  log line records the verdict and rule ID.
- `scripts/client_demo.py`: eligibility calls that preview the T1 approval and T2 denial.

## Why

The agent may only approve after an `ELIGIBLE` result and only deny after `NOT_ELIGIBLE`,
so this function decides every clear-cut case. Keeping it pure and exhaustively tested
means the same input always gives the same, checkable answer.

## How it was built

Test-first: a red commit before each green commit.

## Testing

- Every row of the REQUIREMENTS §8 pre-computed table is a named test case.
- Boundaries: eligible on the refresh date exactly, not eligible one day before.
- Month-end and leap-year clamps, and the order of the algorithm (status is checked before
  role, a missing employee is reported before an unknown item).
- Robustness: all 36 employee and item pairs return a valid verdict.
- Integration tests call the tool through MCP in-process.
- `make check`: format, lint, mypy --strict, tests, coverage ≥ 90%, pip-audit.

## Not in this PR

`flag_for_human_review` (M4).
```
