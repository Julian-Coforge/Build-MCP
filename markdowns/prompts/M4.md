## Part 2: Prompts for your coding agent

### Prompt 1 of 2: The review function and queue

```text
Read markdowns/REQUIREMENTS.md sections 2.3 (review ticket), 5 (escalation codes E1-E11),
6.1 (C3 and C7), 7.4 (contract) and the flag_for_human_review row of 12.1. Read
markdowns/PLAN.md section 5 (what is never logged), and src/it_requests/employees.py for
the code style (errors as data, comments on WHY).

GOAL: implement flag_for_human_review as a plain function with injected dependencies (the
queue file path and the current time), so it is fully unit-testable with tmp_path.

Follow CLAUDE.md: tests first (in tests/unit/test_reviews.py), show them failing, then stop for "go".

FILE: src/it_requests/reviews.py

1. ESCALATION_CODES: tuple of "E1".."E11" (one source of truth).

2. parse_reason(reason: str) -> tuple[str, str] | None
   Valid form: optional whitespace, a code E1..E11 (case-insensitive, returned upper-case),
   a colon, then a non-empty explanation. Return (code, explanation stripped), or None.
   "E6: Phone stolen" -> ("E6", "Phone stolen"); "e9:needs HR" -> ("E9", "needs HR").
   Invalid: "E12: x", "E0: x", "E6 phone stolen" (no colon), "E6:" and "E6:   " (no
   explanation), "phone stolen", "", "E1E2: x". Watch that "E1" does not match the
   start of "E11": use a full-match regex.

3. flag_for_human_review(employee_id: str, request: str, reason: str, *,
                         queue_path: Path, now: datetime) -> dict[str, Any]
   Validation BEFORE anything is read or written, in this order:
   a. request.strip() empty -> {"error": "INVALID_REQUEST", "detail": "request must not be empty"}
   b. parse_reason fails -> {"error": "INVALID_REASON", "detail": "reason must start with a code E1-E11 followed by ': ' and an explanation"}
   employee_id is NOT validated and NOT required to exist (E1 escalations must still be
   recorded, REQUIREMENTS §2.3). Store it stripped, as given; an empty string is allowed.

   Idempotency (§7.4): if a ticket already exists with the same employee_id
   (compare stripped and upper-cased) and the same request (compare stripped), return
     {"review_id": <existing>, "status": "pending", "reason_code": <existing code>, "duplicate": True}
   and write nothing.

   Otherwise append a ticket and return
     {"review_id": "REV-0001" style, "status": "pending", "reason_code": code, "duplicate": False}
   Ticket stored in the file (REQUIREMENTS §2.3):
     review_id, employee_id, request (stripped), reason_code, reason (the explanation),
     status "pending", created_at (now.isoformat())
   review_id = "REV-" + 4-digit number = number of existing tickets + 1.

   Storage:
   - Queue file format: {"tickets": [ ... ]}. A missing file means an empty queue (the file
     is created on the first write, including the parent folder).
   - Write atomically: write to a temp file in the same folder, then os.replace() it over
     the queue file. A crash mid-write can then never leave half a JSON file.
   - If the existing file is unreadable or not valid queue JSON, return
     {"error": "QUEUE_UNAVAILABLE", "detail": "<short reason>"} and do NOT overwrite it
     (never destroy existing tickets to "fix" the file).
   - `now` is injected, so tests control created_at. Explain in a comment why this
     function takes `now` instead of reading the clock: it keeps tests deterministic, and
     the server passes in the real time.

TESTS (tests/unit/test_reviews.py), using tmp_path for the queue file and a fixed `now`
(e.g. datetime(2026, 11, 22, 9, 0, tzinfo=UTC)):
- the first flag returns REV-0001, status pending, reason_code "E6", duplicate False; the
  file contains exactly one ticket with every §2.3 field and the right values
- a second, different flag returns REV-0002
- a duplicate (same employee and request, also with different case or whitespace in the
  employee ID and extra whitespace around the request) returns the SAME review_id with
  duplicate True, and the file still has one ticket
- same employee, different request: a new ticket
- an unknown employee ("E9999") and an empty employee_id are both accepted (E1 must be flaggable)
- invalid reasons (parametrize the invalid list above): INVALID_REASON, and the queue file
  does NOT exist afterwards (nothing written)
- empty and whitespace-only requests: INVALID_REQUEST, and nothing is written
- when both request and reason are invalid, INVALID_REQUEST is returned (validation order)
- parse_reason: parametrize the valid and invalid examples above, including that "E11: x"
  parses as E11 and "E1: x" as E1
- a corrupt queue file (write "not json" to it first): QUEUE_UNAVAILABLE, and the file
  content is unchanged afterwards
- created_at equals the injected now in ISO format
- atomic write: after a successful flag, no temp files are left in the folder

Comment WHY at each non-obvious decision (validation before writing, idempotency key,
atomic replace, not overwriting a corrupt file, injected now).
```

**Why idempotency matters here:** the agent might retry a tool call, or a test request might be rerun for screenshots. Without idempotency, each retry would create another ticket, and the human reviewers would see duplicates. That would also break constraint C7 (at most one escalation per request).

**Why validate before writing:** a rejected call (a bad reason code) must leave no trace. The unit tests check this by asserting the queue file doesn't exist afterwards.

## Part 5: PR description (paste into GitHub)

**Title:** `M4: flag_for_human_review, completing the MCP server`

```markdown
## What

Milestone M4 (brief step 4, fourth tool). With this, the MCP server exposes all four tools
the brief requires (Part 2), each tested as a plain function and through MCP (Part 3).

- `reviews.py`:
  - `parse_reason()` accepts only `E1`–`E11`, then a colon, then an explanation
    (`E11` is never confused with `E1`).
  - `flag_for_human_review()` validates before writing anything (`INVALID_REQUEST`,
    `INVALID_REASON`), accepts unknown or missing employee IDs (E1 must be flaggable), and
    is idempotent: the same employee and request returns the existing `review_id` with
    `duplicate: true`.
  - Tickets follow REQUIREMENTS §2.3 and IDs are sequential (`REV-0001`).
  - The queue file is written atomically (temp file plus `os.replace`), and a corrupt
    queue file is reported as `QUEUE_UNAVAILABLE`, never overwritten.
  - The current time is injected, so tests are deterministic.
- `server.py`: `flag_for_human_review` registered with the §7.4 description. The queue
  path and clock are injected through `build_server()`, and the log line records
  `reason_code`, `review_id` and `duplicate` but never the request text.
- `scripts/client_demo.py` calls all four tools, including a duplicate flag and an invalid
  reason. `make reset-reviews` gives the demo a clean queue.

## Why

This is the only side-effecting tool, so it is built to be safe to call more than once and
safe to call wrongly: duplicate escalations would break constraint C7, and a rejected call
must leave no trace. Escalation is how the agent avoids guessing, so it must be reliable.

## How it was built

Test-first: a red commit before each green commit.

## Testing

- Unit tests cover the first and sequential tickets, duplicates (including case and
  whitespace variants), unknown and empty employee IDs, every invalid reason form, empty
  requests, validation order, a corrupt queue file and no leftover temp files.
- Integration tests cover the tool through MCP (description, ticket written, idempotency,
  errors as data, no request text in the logs), plus two multi-tool paths (T2 denial and
  T3 escalation) through the real protocol.
- `make check`: format, lint, mypy --strict, tests, coverage ≥ 90%, pip-audit.

## Screenshots

Deliverables #3 (server code) and #4 (unit tests passing) were taken from this branch.

## Next

M5: the agent's first hardcoded tool call, with cost tracking and tracing.
```
