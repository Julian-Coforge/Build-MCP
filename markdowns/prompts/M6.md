## Part 5: PR description (paste into GitHub)

Title: `M6: ReAct loop with guards, eval cases and live T1-T4 results`

```markdown
## What

Brief step 5b and Part 4: the agent now chooses its own tools in a Thought / Action /
Observation loop until it calls `final_answer`.

- `agent/guards.py`: pure checks for C1 (approve only after ELIGIBLE), C2 (deny only after
  NOT_ELIGIBLE, rule ID in the reply), C3 (escalation has a real review_id in the reply),
  C6 (8 investigation calls), C7 (one flag) and the decision table's required tool calls.
- `agent/tools.py`: every MCP tool gets a required `thought` argument (stripped before the
  server sees it), plus a strict `final_answer` tool.
- `agent/loop.py`: the loop, the step cap, one chance to correct a rejected answer, and a
  code-driven E11 escalation when the model can't finish safely.
- `agent/trace_format.py`: the printed trace used for deliverable #6.
- `evals/cases.json`, `evals.py`, `scripts/run_eval.py`: T1 to T12 with expected results,
  grading, and the live eval run.
- `server.py`: tool calls now log the agent's `request_id` (sent in `_meta` since M5).

## Why

- The model interprets the request and picks the tools; the guards make sure every final
  decision is backed by what the tools returned in this run. A prompt alone can't
  guarantee that.
- A required `thought` field puts a Thought before every Action in the trace, because
  current models hide their thinking by default.
- `final_answer` returns the decision as data, so the guards check fields instead of
  parsing prose.
- One correction, then a fixed E11 escalation: the agent never ends a run with an
  unchecked decision, and never loops forever.
- The system prompt and tools are cached across steps, which cuts the cost of every step
  after the first.

TDD in four red/green steps (see the commit list). Each red commit holds only failing tests.
```
