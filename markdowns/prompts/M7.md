# M7 Prompt Pack: reflection (the §11 checklist) and the fault-injection demo

**Brief step covered:** 6 and Part 5 ("before finalizing, the agent reviews its own draft").
**Deliverable produced (as LaTeX, not a screenshot):**
- **#8**: reflection evidence. A normal T1 run that logs `REFLECTION: CONFIRMED`, next to a fault-injected T1 run that logs `REFLECTION: REVISED (...)`. These are verbatim trace text and log lines.

**Branch:** `m7-reflection` · **One PR** at the end (text in Part 5).

After the guards accept a final answer, a reflection step reviews the draft reply against the REQUIREMENTS §11 checklist before anything is returned. The reflection step works in two layers:

- **Code checks** run first. They are cheap and deterministic. For example, every date in the reply must appear in a tool observation from this run (C4).
- **One model call** then answers the six §11 questions. It may rewrite the reply.

Reflection may only change the **reply text**. It can never change the decision, the rule ID, the review ID or the reason code. Those fields were already checked by the guards against real tool results. A model-written revision must pass the same guards, or it is discarded.

**Test standard (applies to every prompt):** all tests follow the Test standard in CLAUDE.md:
- one behaviour and one assert per test;
- names in the form `test_<unit>_<condition>_<expected>`;
- `ids=` on every parametrize;
- no `if` or `for` in a test body;
- fakes, not mocks.

`tests/unit/test_test_style.py` must stay green.

### Prompt 2 of 4: The Reflector (one model call, with revision rules)

```text
Read src/it_requests/agent/reflection.py (from Prompt 1), llm.py, guards.py, loop.py,
tests/conftest.py (FakeMessages, build_message) and CLAUDE.md (Test standard).

GOAL: Reflector.reflect() runs the §11 review of one accepted draft and returns the
final answer to send, with a CONFIRMED or REVISED result.

1. In reflection.py:
   ReflectionResult (frozen): status ("CONFIRMED" | "REVISED"), changes: tuple[str, ...],
   final: FinalAnswer, draft_reply: str | None (the reply before reflection),
   answers: dict[str, bool] | None.
   class Reflector, built with llm: LLMClient, tracer, logger.
   reflect(*, request_id, run_id, request_text, answer: FinalAnswer,
           observations: Sequence[Observation]) -> ReflectionResult:
   a. findings = code_findings(answer, observations).
   b. Inside a "reflection" span: ONE llm.call with stage "reflection",
      system=system_blocks(SYSTEM_PROMPT_REFLECTION), tools=[REFLECTION_TOOL], and one user
      message holding: the request text, the observations as JSON, the draft
      (decision, rule_id, review_id, reason_code, draft_reply), and the code findings.
   c. Take the first reflection_verdict tool_use and parse_verdict it. If there is none,
      or it is malformed, log "reflection.unparsed" at WARN and treat it as CONFIRMED (the
      code checks below still run).
   d. candidate reply = verdict.revised_reply if REVISED, else the draft reply. The
      decision, rule_id, review_id and reason_code are ALWAYS copied from `answer`,
      whatever the model returned.
   e. If the model revised: check_final_answer(candidate answer, observations). If it
      returns any code, discard the revision (keep the draft reply), log
      "reflection.revision_discarded" at WARN with the codes, and do not count it as a
      change.
   f. Re-run code_findings on the candidate. If C4_UNSUPPORTED_DATE remains, apply
      remove_sentences_with(candidate, unsupported_dates(...)) and add the change
      "removed unsupported date <date>" (code-made, so the demo can't depend on the model).
      Other findings that remain are logged at WARN as "reflection.unresolved".
   g. status is REVISED when the final reply differs from the draft reply, otherwise
      CONFIRMED. changes = the model's what_changed (if its revision was kept) plus the
      code-made changes.
   h. Log "reflection.result" (status, changes; never the reply text above DEBUG) and set
      span attributes result, changes (joined) and findings.
2. tests/unit/test_reflection.py (add to the file), with LLMClient over FakeMessages and
   a tmp ledger:
   - CONFIRMED verdict on a clean draft gives status CONFIRMED and the unchanged answer.
   - A REVISED verdict with a guard-safe reply gives status REVISED and that reply.
   - A REVISED verdict that also changes the decision field still returns the original
     decision (the copy rule).
   - A REVISED reply that drops the rule ID from a deny is discarded: status CONFIRMED.
   - A draft with an unsupported date and a model that says CONFIRMED: the code removes
     the sentence, status REVISED, changes name the date.
   - No tool_use in the response: treated as CONFIRMED, one WARN "reflection.unparsed".
   - Exactly one model call, ledger stage "reflection".
   - A "reflection" span is the parent of the llm.call span.
   - The reflection.result log line has no reply text.

Tests first, show the failures, STOP and wait for `go`. Then implement and run make check.
```

## Part 5: PR description (paste into GitHub)

Title: `M7: reflection step (§11 checklist) with a labelled fault-injection demo`

```markdown
## What

Brief step 6 and Part 5: before a decision is returned, the agent reviews its own draft
reply against the REQUIREMENTS §11 checklist and logs `REFLECTION: CONFIRMED` or
`REFLECTION: REVISED (<what changed>)`.

- `agent/reflection.py`: pure code checks (every date in the reply must come from a tool
  observation, a denial includes `next_eligible_date`, an escalation quotes its
  `review_id`), the strict `reflection_verdict` tool, and `Reflector`, which makes one
  model call to answer the six §11 questions.
- `agent/loop.py`: reflects on every accepted final answer (never on the fixed fallback
  reply); `--inject-fault` adds a delivery promise to the draft for the demo.
- `agent/trace_format.py`: REFLECTION lines, the draft before reflection, and a
  `[FAULT INJECTED ...]` label.
- `run_agent.py` and `run_eval.py` always reflect; `make agent-fault` runs the demo.

## Why

- §11 requires a self-review before finalizing; deliverable 8 needs a run that confirms
  and one that revises.
- Reflection may only change the reply text. The decision, rule ID, review ID and reason
  code were already checked by the guards against real tool results, so a model revision
  can't undo C1 to C3. A revision that fails the guards is discarded.
- Code checks run alongside the model: an unsupported date is removed by code even if the
  model misses it, so the fault-injection demo is guaranteed and repeatable (PLAN D3).
- The fault run is labelled in the trace, the logs and the span, and eval runs can never
  inject a fault.

## How it was built

TDD in four red/green steps (see the commit list). Every test follows the AAA standard,
and the style guard stays green.

## Testing

- Unit: each code check firing and not firing, sentence removal, the verdict schema and
  parser, the Reflector's confirm, revise, discard and code-fix paths, one model call with
  ledger stage `reflection`, no reply text in logs.
- Integration (scripted fake LLM + real in-process server): T1 confirmed, the fault caught
  by code and by the model, a discarded revision on T2, no reflection on a fallback, and
  M6 behaviour unchanged without a reflector.
- CI never calls the real Claude API.
- Live (Sonnet): T1 to T4 x 1 re-run: _/4, all `CONFIRMED`. Demo: T1 `CONFIRMED`, T1
  fault-injected `REVISED (...)`. Cost: $_____.

## Next

M8: T5 to T12 once each, the cost report, and the submission PDF.
```
